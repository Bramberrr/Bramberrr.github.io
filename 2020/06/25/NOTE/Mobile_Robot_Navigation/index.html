Mobile Robot Navigation in ROS: A* Meets the Dynamic Window

Created2020-06-25
|Post View:

About this project

This was my project for a mobile robotics course at Zhejiang University in 2020. The robot is a small simulated differential-drive vehicle in Gazebo, with a 2D laser scanner. The task was to make it drive itself to any goal clicked on the map, avoiding walls and obstacles along the way, using ROS. The code is on GitHub: Bramberrr/move_robotics.

Navigation is split into the usual two layers:

  • A global planner that finds a route across the whole map with A*.
  • A local planner that follows that route in real time and dodges nearby obstacles with the Dynamic Window Approach (DWA).

The system

Everything starts from one launch file, which brings up these nodes:

Node What it does
Gazebo world Simulates the robot, its wheels and its laser scanner
map_server Serves the occupancy-grid map of the arena
robot_tf Publishes the robot’s pose in the map frame
kinematics Turns velocity commands into left and right wheel speeds
global_planner Plans a path with A* whenever there’s a new goal
local_planner Follows the path with DWA and sends velocity commands
rviz Shows the map, the laser, the path, and lets me click goals

A goal set with rviz’s “2D Nav Goal” tool goes to the global planner, which publishes a nav_msgs/Path. The local planner picks it up and keeps sending Twist commands until the robot arrives.

From velocity to wheel speeds

The local planner thinks in terms of forward speed $v$ and turning rate $\omega$, but the simulated robot is driven by two wheel-velocity controllers. For a differential drive with wheel radius $r$ and half the distance between the wheels $b$:

$$\omega_{L} = \frac{v - b,\omega}{r}, \qquad \omega_{R} = \frac{v + b,\omega}{r}$$

Here $r = 0.08$ m and $b \approx 0.113$ m.

Global planner: A*

The global planner fetches the map from map_server and treats every occupied cell as an obstacle. It plans on a coarser 0.3 m grid, and inflates obstacles by a 0.6 m robot radius so that any path it finds leaves room for the robot’s body. A* then searches the grid with 8-connected moves and a straight-line distance heuristic.

It replans whenever a new goal arrives, and it also offers a ROS service, /course_agv/global_plan, so other nodes can ask it to plan again from the robot’s current position.

Local planner: Dynamic Window Approach

Following the global path exactly isn’t enough: the robot can only change speed so fast, and the laser may see obstacles the map doesn’t have. DWA handles both by searching over velocities instead of positions. Every cycle it:

  1. Picks a local goal. It’s the farthest point on the global path within 1.6 m of the robot (top speed × the 2 s prediction horizon).
  2. Collects obstacles. Every laser point closer than 1.6 m becomes an obstacle, in the robot’s own frame.
  3. Builds the dynamic window. This is every $(v, \omega)$ the robot can reach within the next 0.1 s given its acceleration limits, clipped to its speed limits (−0.5 to 0.8 m/s, up to 100°/s).
  4. Simulates and scores each option. For each sampled $(v, \omega)$ it rolls the motion model forward 2 s and scores the trajectory:

$$\text{cost} = 0.5,\text{heading to goal} + 1.0,(v_{\max} - v) + 1.0,\frac{1}{d_{\min}}$$

Here $d_{\min}$ is the closest the trajectory gets to an obstacle. Any trajectory that would hit the 0.6 m × 0.3 m robot footprint is thrown out.

  1. Sends the best command. The winning $(v, \omega)$ is blended 50/50 with the previous command to smooth out jitter, and the robot stops once it’s within 0.1 m of the goal.

The planning loop runs in its own thread, so the laser and path callbacks never block it. The A* and DWA cores were adapted from the open-source PythonRobotics implementations and wired into ROS: map handling, tf lookups, local-goal selection, laser processing and command smoothing.

Results

Driving to goals while the map is built

In this run, goals are clicked one after another in rviz (left), while Gazebo (right) shows the robot and its laser scan in blue. The occupancy-grid map fills in from the laser as the robot explores, and the robot’s trail shows it weaving through the arena to each goal.

Video (3 min, no sound): rviz on the left with the occupancy-grid map growing as the robot drives, Gazebo on the right with the robot’s laser scan shown in blue.

Replanning around a new obstacle

Here the planned path is shown as a thin yellow line. A box sits in the arena that isn’t part of the original map. Once the laser sees it, it shows up in the occupancy grid, and the planner works out a new route around it.

Video (1.5 min, no sound): the map in rviz with the planned path in yellow; on the right, a box sits in the arena in Gazebo and the robot’s laser sweeps across it.

Summary

Splitting navigation into a global A* route and a local DWA controller let the robot get across the whole arena while still reacting to its speed limits and to obstacles the map didn’t know about. A few small additions made it run smoothly: following a look-ahead point on the path instead of the next waypoint, building obstacles straight from the laser, and blending each new command with the last one.
